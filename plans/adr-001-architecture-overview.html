ADR-001: Arquitetura Geral

Aceito • 2026-05-16 • Autor: Hermes
Última revisão: 2026-05-16

Contexto

Jauri precisa executar aplicações desktop Java usando uma webview nativa como frontend. Diferente de JCEF (embute Chrome, ~100MB+) e JavaFX WebView (limitado, software render), a engine deve ser leve (~15MB), rápida, e aproveitar o ecossistema Java existente.

Decisão

Arquitetura em 4 camadas isoladas, cada uma com responsabilidade única e dependência estrita da camada abaixo:

┌─────────────────────────────────────┐
│  Layer 3: Jauri Runtime            │
│  Orquestra startup/shutdown        │
│  Extrai /static/, sobe HTTP        │
│  Abre webview na URL correta       │
├─────────────────────────────────────┤
│  Layer 2: IPC Bridge               │
│  HTTP localhost (127.0.0.1:PORTA)  │
│  POST /api/invoke → roteia handler │
│  Retorna JSON                      │
├─────────────────────────────────────┤
│  Layer 1: WebView Engine           │
│  JNA → GTK3 + WebKitGTK 4.1       │
│  Cria janela, instancia webview    │
│  Gerencia gtk_main loop            │
├─────────────────────────────────────┤
│  Layer 0: Native Platform          │
│  libgtk-3.so, libwebkit2gtk-4.1   │
│  JVM ou GraalVM native-image       │
└─────────────────────────────────────┘

Regras da arquitetura

  1. Dependência unidirecional: Layer N só conhece Layer N-1. Runtime não fala com JNA direto.
  2. Substituibilidade: Layer 1 (WebView Engine) é a única que sabe de JNA/GTK. Se trocar pra Windows WebView2, só essa camada muda.
  3. Testabilidade: Layer 2 e 3 são testáveis sem GTK (mock das camadas inferiores).
  4. Porta aleatória: HTTP server sempre escuta em porta 0 (SO escolhe). Evita conflito.
  5. Loop GTK na thread principal: gtk_main() bloqueia a thread main. Thread pool do HTTP server é separada.

Consequências

Positivas:
  • Cada camada é pequena (~100-300 linhas cada)
  • Se GTK crashar (segfault), o erro tá numa camada específica
  • Testes unitários do IPC e runtime rodam sem display gráfico
  • GraalVM native-image consegue analisar cada camada separadamente
Negativas:
  • JNA binding é frágil — um tipo errado = segfault sem stack trace
  • Thread do GTK vs threads do HTTP server precisam sincronizar no shutdown
  • Callback de eventos GTK (resize, close) pra dentro do Java é mais complexo que ideal

Alternativas consideradas

AlternativaMotivo da rejeição
Project Panama (JDK 22+)Maturidade baixa, docs escassas, JDK 22+ necessário. Fica pra v2.
Subprocess bridge (C mínimo abre webview)Dependência de binário externo, distribuição complexa.
JNI puroBoilerplate alto, compilação C separada, mais pontos de falha que JNA.
JavaFX WebViewSoftware render, lento, API limitada, dependência do JavaFX module.
JCEF (Chromium Embedded)Pesado (~100MB+), distribuição complexa, Chrome inteiro embutido.
